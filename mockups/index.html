Lumen mockups

One wallet for every way to hold bitcoin: Lightning through NWC, Cashu ecash stored on Nostr (NIP-60), on-chain and Liquid. No account needed to start. Phone, tablet and desktop layouts. Sample data throughout. Accessibility requirements are listed at the end.

Getting started

No account. Adding the first wallet is the whole setup, here a Lightning wallet over NWC. NWC signs with the key inside the connection string, so it needs no Nostr identity.

Adding ecash

Ecash is the only wallet that needs a Nostr identity, so Lumen asks for one at this point and not before. A new key is shown once and must be saved before the wallet is created. Each wallet screen repeats the Send, Receive and Scan actions of Home, with that wallet preselected.

Send

Lumen picks the wallet that can pay. The user can switch before confirming.

Receive, settings and lock

Receiving starts from the network, then the wallet that gets the funds. Settings is the same for everyone: the Nostr identity lives in the ecash wallet, not here. With App lock on, Lumen opens on the lock screen and shows the system prompt (biometrics, with the device passcode as fallback).

Largest text size

The home screen with the system text size at 200%. Body text doubles, large amounts grow less, rows stack instead of truncating, and the screen scrolls.

Tablet

Between 600 and 839 px wide, for example a tablet in portrait. Same navigation as the phone, with lists side by side in two columns. Send and receive open in dialogs, like on desktop.

Desktop

From 840 px wide: desktop, web, and tablets in landscape. A sidebar lists every wallet and replaces the back button. Send and receive open in dialogs over the current page.

Layout rules

Rules the screens above follow, to keep when adding new ones.

  • Three layouts, chosen by window width. Phone under 600 px: one column, back button, transaction flows full screen. Tablet from 600 to 839 px: same navigation as the phone, lists in two columns, transaction flows in dialogs. Desktop from 840 px: sidebar with every wallet instead of a back button, transaction flows in dialogs over the current page. The width decides, not the device: a tablet in landscape gets the desktop layout.
  • Same content at every size. A larger screen shows more at once, never different features. Settings, Backup and every action exist in all three layouts.
  • Scan works without a camera. On desktop, Scan uses the webcam when there is one and always offers to paste instead. The Send dialog also accepts a pasted invoice, address or token.
  • Balance screens are left-aligned. Home and every wallet screen share one layout: balance on the left, then Send, Receive and Scan, then lists. On a wallet screen the wallet icon takes the place of the "Total balance" label.
  • Transaction screens are centered. Amount entry, review, payment result and receive put the amount alone in the center, with the keypad or QR code below.
  • Same actions everywhere. Send, Receive and Scan keep the same order and position on every balance screen. On a wallet screen they preselect that wallet.
  • The Nostr identity belongs to the ecash wallet. No account is needed to start, and the app has no global identity. Each ecash wallet shows its own identity under Backup, so several identities simply mean several ecash wallets.
  • Restoring happens inside each wallet type. The app has one entry point, Add a wallet. Each type then offers to create or restore: ecash signs in with Nostr, on-chain and Liquid restore from a seed. NWC always connects an existing wallet.
  • Locked means nothing shows. The lock screen shows no balance or activity, and while App lock is on the app switcher preview is hidden. The Unlock button stays on screen so a dismissed system prompt can be opened again.

Accessibility requirements

Target: WCAG 2.2 AA on iOS and Android, to be tested with VoiceOver, TalkBack, Switch Access and a hardware keyboard.

  • Contrast. Text at least 4.5:1, icons, field borders, focus rings and selected states at least 3:1, in both themes. Every color token in styles.css meets this.
  • Touch targets. At least 48 by 48 dp for every control (Flutter's kMinInteractiveDimension), including small icon buttons like copy.
  • Text size. Follow the system text scale up to 200% (see frame 16). No fixed heights around text, every screen scrolls, rows stack when they no longer fit, and large amounts scale less than body text.
  • Labels. Every icon-only button has a Semantics label or a tooltip. Decorative icons and avatar initials are excluded from semantics.
  • Rows and amounts. Each list row is read as one item (MergeSemantics). Amounts are always read with their unit and direction: "received 21,000 sats", never "+21,000". "≈" is read as "about".
  • Announcements. The amount typed on the keypad and the payment result are live regions, so screen reader users hear them without moving focus.
  • Never color alone. The wallet type is shown with an icon and a name, direction with a sign and words, and errors with text next to the field.
  • Errors. Shown inline under the field, linked to it, announced, and written as a fix ("This is not an NWC connection string. It should start with nostr+walletconnect://").
  • Focus. A visible focus ring on every control, and a reading and focus order that goes top to bottom. Opening a screen moves focus to its title.
  • Keyboard. Every action works with the keyboard alone. Dialogs keep focus inside, close with Escape and return focus to the button that opened them. The page behind a dialog is inert. Hover never shows information that focus does not.
  • Zoom and reflow. Zooming moves to the next smaller layout instead of scrolling sideways: the desktop at 200% zoom uses the tablet layout, and at 400% (320 px wide) the phone layout.
  • Tables. Activity on desktop is a real table with column headers, so screen readers can read it cell by cell.
  • QR codes. Always paired with the text they encode and a copy button. Scanning always has a paste alternative.
  • Secrets. The secret key is hidden by default and never read aloud unless the user asks to show it. Copying it clears the clipboard after a minute.
  • System settings. Respect reduce motion (MediaQuery.disableAnimations), bold text and high contrast (MediaQuery.highContrast). The mockups also handle Windows high contrast mode.
  • Time limits. No action expires while the user is on the screen. Expiring invoices show their remaining time and can be refreshed in one tap.
